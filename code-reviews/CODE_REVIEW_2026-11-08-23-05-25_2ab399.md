## 发现

### [P2] 停止后仍会启动排队任务

[Scheduler.cs 第 41–58 行](../src/Cronlet/Scheduler.cs#L41-L58) · [第 319–341 行](../src/Cronlet/Scheduler.cs#L319-L341) · [第 253–268 行](../src/Cronlet/Scheduler.cs#L253-L268)

`Stop` 设置停止标志并终止现有进程。该进程完成后，`Complete` 仍会为 `Pending` 调用 `FireLocked`。新进程在 `proc.Start()` 之后才检查停止标志。定向测试以 `queue` 积压一次运行，调用 `Stop` 后观察到第二条 `task-start`。如果新进程先于终止请求开始执行，命令可能产生副作用。

停止时取消待补跑请求，并在派发入口拒绝新的运行名额。已登记但尚未启动的名额也应能取消，且启动与停止需要明确的先后关系。

### [P2] kill 策略会放行已被替换的启动请求

[Scheduler.cs 第 209–235 行](../src/Cronlet/Scheduler.cs#L209-L235) · [第 239–259 行](../src/Cronlet/Scheduler.cs#L239-L259)

调度先登记 `Running`，后台执行随后才创建进程。在这段间隔内，下一次触发采用 `kill` 时没有已启动的进程可终止，只会覆盖 `RunId`。原请求进入 `ExecuteAsync` 后只用 `RunId` 决定是否登记进程，随后仍会调用 `Start()`。若进程已登记但尚未启动，当前的 `Kill` 也可能失败并被忽略。定向测试在第一次启动前登记替换请求，两次请求均启动了子进程。

将待启动、已启动和已取消的状态绑定到每次运行。替换时撤销未启动请求，对已启动进程执行终止操作，并确保过期请求不能再启动。

### [P2] 重载通知可能在调度开始等待前丢失

[Scheduler.cs 第 138–166 行](../src/Cronlet/Scheduler.cs#L138-L166) · [第 406–430 行](../src/Cronlet/Scheduler.cs#L406-L430)

循环先在锁内读取旧的队列状态，随后在 `WaitOrWakeAsync` 中重新取得唤醒任务。若重载在两步之间替换队列并触发唤醒，循环会等待重载之后的新唤醒任务，仍按旧队列的延迟休眠。从空配置重载可因此延迟至 30 秒，原有下次触发较远时延迟至 60 秒，落在这段窗口内的 cron 触发可能迟到或被跳过。定向测试复现了先发出通知再订阅时，等待仍走完整个 500 毫秒；上述最长延迟依据循环的等待上限推导。

在同一临界区读取下次触发时间和当前唤醒任务，把两者作为一份快照传给等待逻辑。

### [P3] 单一命令入口缺少迁移说明，工作目录文档与实现不一致

[README.md 第 21–32 行](../README.md#L21-L32) · [ConfigValidator.cs 第 15–20 行](../src/Cronlet/ConfigValidator.cs#L15-L20) · [Scheduler.cs 第 449–454 行](../src/Cronlet/Scheduler.cs#L449-L454)

已实测旧 `script` 和过渡字段 `script_file` 均报 `command 不能为空`。复审回复说明现有部署已手动迁移，因此保留单一字段是合理的取舍。但 README 未说明迁移方法，`cwd` 一栏仍称默认使用脚本目录。实际默认是 exe 目录，显式设置 `cwd` 后，命令中的相对路径以该目录为基准。

在 README 增加简短迁移说明，给出 `command = "& './scripts/Daily Jobs/report.ps1'"` 之类的含空格路径示例，并说明如何用 `cwd` 保留原脚本的工作目录。

## 实现方案比较

| 领域 | 评估 |
| --- | --- |
| 调度和重载 | 保留单一调度状态锁和按任务实例归属补跑的设计。已用真实子进程复测，成功重载会丢弃旧补跑，30 秒超时后会恢复一次旧补跑。当前更值得补齐的是状态快照与唤醒订阅的原子性，以及启动名额与进程生命周期的衔接。 |
| 进程生命周期 | 只在完成回调增加停止判断可以拦住一条补跑路径，已经登记的启动仍可能越过停止或替换。更稳妥的方案是为每次运行保留身份和可取消的启动名额，由启动、停止和替换共同更新。应让进程树终止与等待在调度状态锁外执行，并对同一任务的启动和撤销建立明确的同步边界。 |
| 配置入口 | 单一 `command` 将路径解释交给 PowerShell，消除了上一轮两类歧义。针对已经完成迁移的单部署，补齐迁移说明比恢复旧字段或路径推断更合适。脚本执行测试可直接覆盖实际的 `ForCommand` 入口，目前仅用于测试的 `ForScript` 可以随之删除。 |
